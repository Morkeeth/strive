# Android browser compatibility candidate

Local branch from production 5d6d239. No release, schema change or production run mutation.

The affected Android browser/version has not been identified. The reported white screen is not yet proved fixed on his phone. Pixel emulation changes the device profile, not the JavaScript engine.

## What failed

On the pinned baseline, removing APIs absent in Chrome 80 stops startup with `crypto.randomUUID is not a function`; no public cards load. The SDK and app also contain logical assignment syntax newer than Chrome 80. The original production build fails an ES2019 parse scan. Static public introduction text was already present in the baseline: the local baseline is stalled, not literally all white.

## Change

- Compile every deployment JS file and executable inline script with pinned esbuild 0.25.12, target ES2019 and Chrome 80. A pinned Acorn 8.15.0 ES2019 scan of the final output fails the build if syntax regresses. This includes lazy code and Supabase, not only index.html. Source development files remain modern; use `npm run build` and serve dist for compatibility checks.
- Build the installed, lockfile-pinned Supabase 2.117.3 UMD locally. Its same-origin script and preload get the SHA-384 integrity of the compiled bytes. No live CDN dependency remains in the deployment. Existing CSP hashes are computed after compilation; no eval permission is added.
- Load ES5 error/rejection handlers before startup. A constant recovery message lives outside the SPA root and does not erase an open draft or owner view. Static main content and a noscript explanation remain when JS is disabled. No error strings, URLs, queries, fragments or owner data are put in the message.
- Supply missing Array/String.at, String.replaceAll, Object.hasOwn, DOM replaceChildren and crypto.randomUUID. UUIDs use getRandomValues only, preserving version/variant bits; no Math.random fallback.
- Convert the lazy local image engine to a classic script and promise-based WASM setup, avoiding top-level await and import.meta. No font/text is sent to external rendering services.
- CSS :has rules are progressive enhancements. An unsupported rule is ignored by Chrome 80; no script calls querySelector/closest with :has and no baseline visibility depends on it. Visual parity of those enhancements on an actual Chrome 80 device is not claimed.
- No client error beacon is added. There is no personal-data-free collection store approved for this repair; recovery and compatibility do not require one. The guard uses no storage, networking, cookies or identifiers.

The target/syntax transformation follows https://esbuild.github.io/api/#target; API polyfills are separate because a syntax target does not add browser APIs.

ES2019 syntax coverage is the fallback gate, not proof of every browser runtime behavior.
